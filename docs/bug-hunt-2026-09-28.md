## D1 · `Deal.create` accepts `stage: "closed_won"`, bypassing every transition guard

WHAT WE DID: called `Deal.create` with `title: "T6-hunt-B6-0334"`, a party we created, `stage: "closed_won"`,
`value: 1`. Then `Deal.get` on the new id, and again on a later login.

EXPECTED: rejected, or started at `new`. Deal stage is a state machine: moving a deal to
`closed_won` requires `Deal.mark_won.{qualification|proposal|negotiation}.closed_won`, which check the
source stage. The sibling document already enforces this: `Quotation.create` with `status: "accepted"`
returns "Quotation.status is a state machine and cannot be set on create; it starts at 'draft'."
`Deal.update` also refuses every `stage` value (`87d456e5`).

ACTUAL: created. It reads back `stage: "closed_won"`, `value: 1.0`, `currency: "INR"`, both times.
The deal never passed through `new`, `qualification`, `proposal` or `negotiation`.

WHY THIS MATTERS FOR AN AGENT: this is the one path where stage can be written directly, and it's
the path an agent takes when told "log the Acme deal we just closed". A won deal with no history
gets into win rate, won revenue and closed-this-month, and nothing marks it as fabricated. The
platform refuses the same move on update and on the quotation, so the agent gets no hint that create
is the exception.

IDS: deal `42249ec8-28a6-429e-9368-03204cdd28ad` (T6-hunt-B6-0334). Refusal for comparison:
`Quotation.create` B10 in `docs/bug-hunt-2026-09-28.jsonl`.

## D2 · `sort_order` on `Item.list`, `Pipeline.list` and `AddressBook.list`: every legal value is a 500

WHAT WE DID: compared `sort_order` across all 49 list schemas. 46 declare
`{"type": "string", "enum": ["asc", "desc"]}`. `Item`, `Pipeline` and `AddressBook` declare
`{"type": "number", "default": 0}`. We called each of those three with `sort_order` = `0`, `1`, `-1`
and `"desc"`, `limit: 3`.

EXPECTED: numeric values sort, or the schema matches the other 46 lists.

ACTUAL: `0`, `1` and `-1` all return `Item.list: Internal server error.` (and the same for Pipeline
and AddressBook), with no error code. `0` is the schema's own default. `"desc"` returns
`invalid_arguments`, as the schema says it should. No value of `sort_order` works on these three lists.

WHY THIS MATTERS FOR AN AGENT: `Item.list` is how the agent resolves a product before quoting. A
client that fills schema defaults, or an agent that asks for "cheapest first", gets a 500 on the
whole call, not an unsorted page. The error looks like an outage, so the agent retries or gives up
on the item.

IDS: no records. Calls are in the evidence log, probes "A2 sort_order" and "C sort_order".

## D3 · List schemas advertise create-time defaults, including unresolved placeholders, on their filters

WHAT WE DID: for every list tool whose `inputSchema` gives a filter a `default`, we called the list
twice: once with no filters, and once with the advertised defaults filled in, as a schema-driven
client does. Then we sent each default on its own (Deal, Party, Quotation, SalesOrder, AgentSession).

EXPECTED: a list filter has no default, since "no filter" is the default. Otherwise sending the
advertised default leaves the result unchanged.

ACTUAL: the defaults are the create-time field defaults copied onto the filters. Two of them are
placeholders the server doesn't resolve on reads:

- `Deal.list` with `currency: "locale:base_currency"` returns 0 of 143 deals, even though 142 of them
  are INR, the base currency. The same happens with `Party.list` `currency_id` (0 of 195) and
  `Quotation.list` `currency_code` (0 of 103).
- `Quotation.list` and `SalesOrder.list` with `date: "today"` return `invalid_arguments`. The same
  happens on `AddressBookEntry.list` and `ContactGroupMember.list` with `added_at: "today"`.
- All defaults together: `Deal.list` 143 → 0, `Party.list` 194 → 0, `AgentJob.list` 1208 → 0,
  `AgentPersona.list` 102 → 0, `AgentSession.list` 2159 → 3, `Item.list` 103 → 1, `Activity.list`
  178 → 23, `Lead.list` 144 → 50, `AgentEscalation.list` 26 → 12.
- Non-placeholder defaults narrow quietly: `stage: "new"` 143 → 69; `SalesOrder.list` `status:
  "draft"` 312 → 2; `AgentSession.list` `actor_kind: "anonymous"` 2160 → 57.

WHY THIS MATTERS FOR AN AGENT: MCP clients and LLM tool-callers routinely fill in schema defaults.
With them, "how many deals do we have" returns `total: 0`: a well-formed, confident answer with
nothing wrong in it that the agent can see. On Quotation and SalesOrder the whole list call fails
instead.

IDS: no records. Probes "A3 defaults sent" and "C default …" in the evidence log.

## D4 · `AgentSession.update` stores negative tool-call, token and cost counters

WHAT WE DID: created `AgentSession` "T6-hunt-session", then called `AgentSession.update` with
`total_tool_calls: -7`, `estimated_cost: -3.5`, `total_input_tokens: -100`. Read it back, then again
on a later login.

EXPECTED: rejected. These are usage counters, and `Deal.create` already enforces the same idea
("Value cannot be negative"). Arguably they shouldn't be writable through `update` at all, since the
platform maintains them.

ACTUAL: accepted. It reads back `total_tool_calls: -7.0`, `estimated_cost: -3.5`,
`total_input_tokens: -100.0`, both times. The `update` schema declares them as plain `number` with no
`minimum`.

WHY THIS MATTERS FOR AN AGENT: session counters are what spend caps and cost reports are built on.
One negative write cancels out real usage in any sum, so a run that was cut off for cost can look
cheap, and a runaway agent can hide its own spend.

IDS: session `c38e1b63-686a-469a-ba9c-48f0f363ba8f` (T6-hunt-session).

## D5 · `Deal.create` accepts any currency string

WHAT WE DID: called `Deal.create` with `title: "T6-hunt-B5-0332"` and `currency: "ZZZ"`. Read it back,
then again on a later login.

EXPECTED: rejected as an unknown currency. The schema is `{"type": "string", "default":
"locale:base_currency"}`, with no enum and no pattern.

ACTUAL: created and stored as `"ZZZ"`. The deal book now reads INR 142, ZZZ 1.

WHY THIS MATTERS FOR AN AGENT: pipeline totals are sums over `value` grouped or filtered by
currency. An agent that writes "Rs" or "rupees" or mistypes "IRN" creates a deal that drops out of
every INR total with no error, so the pipeline is understated and nothing shows why.

IDS: deal `2573d64d-af43-4ce7-b9c9-a95756a432af` (T6-hunt-B5-0332).

## D8 · Guard and validation errors carry no error code, and point to REST paths, not tools

WHAT WE DID: triggered three kinds of rejection and inspected `error.data`:

1. an unknown `sort_by` on `Deal.list` and `Party.list`;
2. `Quotation.create` with `status: "accepted"`;
3. `AgentSession.update` with `status: "closed"`.

EXPECTED: a classified code, as other validation failures have: `invalid_arguments` for bad
probability or a missing foreign key, `invalid_transition` for a guarded move. Also, since the caller
is on MCP, directions to the tool that does the job.

ACTUAL: all three come back with `error.data` = `{}`, so a client sees no code. The messages are
helpful as text. The state guards, though, say "Use POST /api/Quotation/{id}/transition" and
"Use POST /api/AgentSession/{id}/transition". Those are REST routes an MCP caller cannot reach. The
tools that do the job are `Quotation.accept.sent.accepted` and `AgentSession.close.active.closed`.
The D2 500s also have no code.

WHY THIS MATTERS FOR AN AGENT: agents decide what to do next from the error code: fix the arguments,
try a transition, or give up. With no code, a correctable mistake looks like an unknown failure.
When the agent does follow the message, it looks for a tool called "transition" that doesn't exist.

IDS: no records. Probes "A5 sort_by", "C sort_by", "B10", "B13".

`assignee_user_id` and `sla_minutes`. Then we compared our own ESC-2026-00026 with team 04's
ESC-2026-00025.

EXPECTED: an escalation that `create` accepts reaches a human. `AgentEscalation.create` requires only
`session_id` and `reason`; `channel` is optional, with no enum.

ACTUAL: 25 rows have `channel` set, and all 25 have `raised_at`, an assignee and an SLA. ESC-2026-00026

reports it as overdue.
